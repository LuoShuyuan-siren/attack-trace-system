# 成员5 ↔ 成员6 接口说明

**目标读者**: 成员6（集成 / 上层编排 / 持久化层）  
**目的**: 明确成员5交付的 Parser 与 Analyzer 的输入/输出契约，使成员6可以**零侵入**地集成调用

---

## 1. 接口总览

成员5 与成员6 的边界非常清晰——只通过两个 Pydantic Schema 通信：

```
┌─────────────────┐   parse(Path)   ┌──────────────────┐
│   原始流量文件    │ ──────────────► │   NormalizedEvent │
│  PCAP/Zeek/Suricata│                │   (Pydantic)      │
└─────────────────┘                  └────────┬───────────┘
                                              │
                                              │ analyze(events)
                                              ▼
                                     ┌────────────────────┐
                                     │   DetectionResult  │
                                     │   (Pydantic)       │
                                     └────────┬───────────┘
                                              │
                                              ▼
                                       ┌──────────────┐
                                       │   成员6 编排层  │
                                       └──────────────┘
```

**成员6 无需修改任何现有代码，直接调用即可。**

## 2. 输入契约：Parser → Analyzer

### 2.1 Parser 输出：`list[NormalizedEvent]`

**Schema 定义**: `backend/app/schemas/event.py`

```python
class NormalizedEvent(BaseModel):
    event_id: str                          # "evt-<uuid>"
    timestamp: datetime                    # UTC，带 tzinfo
    source_type: Literal["host_log", "host_behavior", "network_traffic"]
    source: str                            # "pcap" | "zeek" | "suricata"
    host: HostInfo                         # 默认实例
    event_type: str                        # 详见下表
    subject: SubjectInfo | None
    object: ObjectInfo | None
    network: NetworkInfo | None            # 流量事件必填
    action: str
    raw_data: dict[str, Any]               # 协议层细节
    severity: Literal["info","low","medium","high","critical"]
    attack: AttackInfo | None
    tags: list[str]
```

### 2.2 Parser → Analyzer 事件类型映射

每个 Parser 输出若干 `event_type`，对应到不同 Analyzer：

| Parser | event_type | 含义 | 进入哪些 Analyzer |
|--------|-----------|------|-------------------|
| PcapParser / ZeekParser / SuricataParser | `network_flow` | TCP/UDP 通用连接 | `ConnectionAnalyzer` |
| PcapParser（基于端口启发式）/ ZeekParser（dns.log）/ SuricataParser（dns 事件） | `dns_query` | DNS 查询 | `DnsAnalyzer`、`ConnectionAnalyzer` |
| PcapParser（payload 启发式）/ ZeekParser（http.log）/ SuricataParser（http 事件） | `http_request` | HTTP 请求 | `HttpAnalyzer`、`ConnectionAnalyzer` |
| PcapParser | `icmp_packet` | ICMP 数据包 | `IcmpAnalyzer`、`ConnectionAnalyzer` |
| ZeekParser（ssl.log）/ SuricataParser（tls 事件） | `tls_handshake` | TLS 握手 | `ConnectionAnalyzer`（仅用作连接统计） |
| SuricataParser（alert 事件） | `alert` | Suricata 告警 | 暂不进入成员5分析器（成员6 可单独路由） |
| SuricataParser（flow 事件） | `network_flow` | flow 记录 | `ConnectionAnalyzer` |

### 2.3 各 Parser 的 `raw_data` 契约

Pydantic 不约束 `raw_data` 内容，但成员5 的 Analyzer **依赖**以下字段：

#### `raw_data["dns"]` (Dcit)

被 `DnsAnalyzer._extract_dns_info()` 读取：

| 字段 | 类型 | 说明 |
|------|------|------|
| `query` 或 `query_name` | str | 查询域名（Suricata/Zeek/Pcap 分别用不同 key） |
| `query_type` | str | "A" / "AAAA" / "TXT" 等 |
| `rcode` / `rcode_name` / `rcode_num` | str | "NOERROR" / "NXDOMAIN" / "3" |

#### `raw_data["http"]` (Dict)

被 `HttpAnalyzer._extract_http_info()` 读取：

| 字段 | 类型 | 说明 |
|------|------|------|
| `method` | str | "GET" / "POST" 等 |
| `host` | str | Host 头 |
| `uri` | str | 请求 URI |
| `user_agent` | str | UA 头 |
| `status_code` | int | 响应状态码 |
| `content_length` | int | 请求体大小 |

#### `raw_data["icmp"]` (Dict)

被 `IcmpAnalyzer` 直接读取：

| 字段 | 类型 | 说明 |
|------|------|------|
| `type` | int | ICMP type 字段 |
| `code` | int | ICMP code 字段 |
| `payload_hex` | str | payload 十六进制（PcapParser 输出） |

### 2.4 `network` 字段契约

所有流量事件的 `network` 字段由 Parser 填充，**Analyzer 仅依赖此字段**：

```python
class NetworkInfo(BaseModel):
    src_ip: str | None
    src_port: int | None
    dst_ip: str | None
    dst_port: int | None
    protocol: str | None                  # "tcp" / "udp" / "icmp"
```

### 2.5 兼容性保证

| 维度 | 保证 |
|------|------|
| `NormalizedEvent` 字段名 | **已冻结，不修改**（成员5 审计已确认零公共接口变更） |
| `raw_data` 子字典 key | 向后兼容：成员5 Analyzer 同时接受 `query` / `query_name`、`rcode` / `rcode_name` 等多种 key 命名 |
| 缺字段处理 | Analyzer 对每个字段做 `safe_str` / `safe_int` 容错，缺失字段视为该指标不触发 |

## 3. 输出契约：Analyzer → 成员6

### 3.1 Analyzer 输出：`list[DetectionResult]`

**Schema 定义**: `backend/app/schemas/detection.py`

```python
class DetectionResult(BaseModel):
    detection_id: str                     # "det-<uuid>"
    timestamp: datetime                    # 告警产生时间（UTC）
    analyzer: str                          # "dns_analyzer" / "http_analyzer" / "icmp_analyzer" / "connection_analyzer"
    detection_type: DetectionType           # 详见 4.1
    title: str                             # 人类可读标题
    description: str | None
    severity: SeverityLevel                 # "info" | "low" | "medium" | "high" | "critical"
    confidence: float                       # [0.0, 1.0]
    related_event_ids: list[str]            # 关联的 NormalizedEvent.event_id（前 50 个）
    related_entity_ids: list[str]           # 实体 ID 关联（成员5 不填，留给成员6）
    evidence: dict[str, Any]                # 可解释证据（详见 4.2）
    attack_technique_id: str | None         # MITRE ATT&CK 技术 ID
    tags: list[str]
```

### 3.2 关键字段填充规则

| 字段 | 填充来源 |
|------|---------|
| `analyzer` | 由 `BaseAnalyzer.name` 提供（如 `"dns_analyzer"`），**Analyzer 自动设置** |
| `timestamp` | **Analyzer 自动设置**为 `datetime.now(UTC)` |
| `detection_id` | 自动生成 UUID |
| `confidence` | 公式 `base + score × increment`，由 `TrafficAnalyzerBase._make_detection()` clamp 到 [0, 1] |
| `related_event_ids` | Analyzer 自动从前 50 个触发事件取 `event_id` |
| `attack_technique_id` | 仅在明确 ATT&CK 技术时设置（详见 4.3） |
| `evidence` | 关键可解释字段（详见 4.2） |

### 3.3 成员6 需自行处理的部分

成员5 **不**做以下事情，成员6 需自行编排：

1. **去重**：同一攻击事件可能产生多条 `DetectionResult`（如 HTTP Beacon + 高频请求），需要按 `related_event_ids` 或 `evidence` 去重
2. **持久化**：将 `DetectionResult` 存入数据库 / 推送到告警平台
3. **告警路由**：按 `severity` / `tags` 分发到不同通知渠道
4. **ATT&CK 完整映射**：成员5 仅在明确技术时填 `attack_technique_id`，广义异常行为 `attack_technique_id=None`，成员6 可基于 `tags` 补充完整矩阵映射
5. **跨攻击关联**：成员5 分析单次 `analyze()` 调用内的全部事件，跨文件/跨时间的关联由成员6 在编排层实现

## 4. 关键字段详细说明

### 4.1 `detection_type` 取值

| 取值 | 含义 | 成员5 使用场景 |
|------|------|----------------|
| `"anomaly"` | 一般异常 | DNS 高频、HTTP 高频、ICMP 高频、Connection 高频（非攻击特征） |
| `"suspicious_behavior"` | 可疑行为 | DNS/HTTP/ICMP 隧道、Beacon、端口扫描、大范围连接、非常用端口、长连接 |

## 5. 端到端集成示例（成员6 视角）

```python
"""
成员6 集成示例：把原始流量变成结构化告警，存入数据库。
"""
from pathlib import Path
from datetime import datetime, timezone

from app.parsers.traffic import (
    PcapParser, ZeekParser, SuricataParser,
)
from app.analyzers.traffic import (
    DnsAnalyzer, HttpAnalyzer, IcmpAnalyzer, ConnectionAnalyzer,
)
from app.schemas.event import NormalizedEvent
from app.schemas.detection import DetectionResult


class TrafficAnalysisPipeline:
    """成员6 编排示例：解析 → 分析 → 持久化"""

    def __init__(self):
        self.parsers = {
            ".pcap": PcapParser(),
            ".pcapng": PcapParser(),
            ".cap": PcapParser(),
            ".log": ZeekParser(),
            ".json": SuricataParser(),
            "eve": SuricataParser(),
        }
        self.analyzers = [
            DnsAnalyzer(),
            HttpAnalyzer(),
            IcmpAnalyzer(),
            ConnectionAnalyzer(),
        ]

    def run(self, source: Path) -> list[DetectionResult]:
        # 1. 按文件类型选择 Parser
        parser = self.parsers.get(source.suffix.lower())
        if parser is None:
            raise ValueError(f"Unsupported file type: {source.suffix}")

        events: list[NormalizedEvent] = parser.parse(source)

        # 2. 跑全部分析器
        detections: list[DetectionResult] = []
        for analyzer in self.analyzers:
            detections.extend(analyzer.analyze(events))

        # 3. 成员6 自定义：去重 / 持久化 / 路由告警 ...
        # （此处省略，详见成员6 模块）

        return detections


# 使用
if __name__ == "__main__":
    pipeline = TrafficAnalysisPipeline()
    detections = pipeline.run(Path("captures/sample.pcap"))

    for d in detections:
        print(f"[{d.severity}] {d.title} "
              f"(confidence={d.confidence:.2f}, attack={d.attack_technique_id})")
```

## 6. 接口稳定性承诺

| 维度 | 承诺 |
|------|------|
| `NormalizedEvent` Schema | **冻结**，成员5 不再修改公共字段（已审计确认） |
| `DetectionResult` Schema | **冻结**，成员5 不再修改公共字段（已审计确认） |
| `BaseParser.parse()` 签名 | **冻结** |
| `BaseAnalyzer.analyze()` 签名 | **冻结** |
| `raw_data` 子字典 key | 向后兼容，新版 Parser 可加 key，但已存在的 key 含义保持不变 |
| 新增 Analyzer | 可能新增（如 FTP/SMTP），但不影响现有调用 |
| 新增 detection_type | 仅扩展 `Literal` 联合类型，成员6 需同步更新类型定义 |

**若成员5 后续需破坏接口，会提前 1 个迭代周期向成员6 发出 BREAKING CHANGE 通知。**

## 7. 常见集成问题 FAQ

**Q1: Parser 输出 0 条事件怎么办？**
A: 检查文件是否存在、扩展名是否在 Parser 支持列表内、空文件会返回 `[]`。Analyzer 对空列表安全（返回 `[]`）。

**Q2: 同一 IP 触发了多条告警如何处理？**
A: 成员5 **不去重**，按 `related_event_ids` 自行去重。推荐按 `(src_ip, event_type, hour_bucket)` 聚合。

**Q3: `confidence` 数值代表什么？**
A: 线性 `base + score × increment`，值越高越可信。范围 [0, 1]，由 `TrafficAnalyzerBase._make_detection()` clamp。

**Q4: `evidence` 中的 `score` 字段如何使用？**
A: `score` 是该 Analyzer 内部评分（不是 `confidence`），由成员5 内部加权计算。成员6 可用于二次过滤（如 `score >= 5` 才推送），但 `confidence` 是更标准的对外指标。

**Q5: 阈值不合适怎么办？**
A: **不要修改全局默认**，构造 Analyzer 时传入自定义 thresholds 实例（详见 `快速开始指南.md` 第 5 节）。修改 `config.py` 默认值会影响所有调用方。

**Q6: 如何扩展检测能力？**
A: 继承 `TrafficAnalyzerBase` 实现新 Analyzer，遵循 `analyze(events) -> list[DetectionResult]` 契约。

**Q7: 跨文件的攻击关联如何做？**
A: 成员5 不做。成员6 在编排层按 `src_ip` / `dst_ip` / `time_window` 自建关联表，或借助成员6 的攻击图模块。
